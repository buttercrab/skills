# Evidence and maintenance of the repository library

The library contains original contextual annotations of inspected primary sources and explicitly labeled leads. Repository cases show possible mechanisms, not a ranking of project quality. Standards, documented practice and studies have different evidential scope. No card establishes that this operating skill improves outcomes in general.

## Resource lifecycle

Use [the card format](../library/FORMAT.md) when curating. Canonical cards generate the browse and JSON indexes; do not hand-edit generated views. Keep stable IDs when updating a source, note consequential version or access changes, and distinguish curated, candidate, needs-review and retired entries.

For a repository case, inspect substantive artifacts along a real change path: contributor/entry information, authoritative input or implementation, and a relevant test/docs/configuration/distribution boundary. A root listing establishes names, not maintainability. Pin repository source to an exact revision when possible; mutable documentation needs an inspection date and scope. Do not call a timestamp update revalidation.

For a guide or standard, inspect the precise rule, normative status, version and exceptions. For a study, inspect methods, population, task and outcomes before adopting an empirical claim. An abstract or inaccessible full text can be a lead with a stated gap, not a receipt for full-method inspection. Repeated reports from the same underlying study are not independent corroboration.

Reading source/configuration establishes intended mechanics only. Do not promote it to an executed check, effective protection, current release or production observation. Retain historical inspection attribution when carrying earlier evidence forward; do not label it freshly verified because its URL still exists.

## Revise from actual work

Record the request, selected resources/portions, consequential question/answer, actual finding or revision and its verification limits. Separate a misleading annotation, ignored human direction, scope drift, setup failure and a real product defect. Change the smallest instruction or card warranted by the evidence; do not grow a universal checklist from every example.

A project trial should return findings to the skill/library at its stated stopping point. It does not silently become a product maintenance campaign. Preserve earlier frozen package/evaluation snapshots and label later revisions. Development fixtures, source reviews and structural tests are useful checks, not proof of superiority or ecosystem-wide recall.

Refresh mutable tool/standard claims when relevant versions or ownership change. Keep inaccessible material and weak coverage visible. New discoveries enter as leads until the relevant mechanism is inspected; no automated refresh, installation, publication or scheduled maintenance is implied.
