# Verify the promise made by the design

Choose checks from the requested result. A brief, static concept, interactive prototype, and integrated product support different claims. Use existing tools and tests where suitable. This is a menu of meaningful checks, not a requirement to run every check on every task.

## Evaluate human direction and execution separately

Compare consequential answers with the output. Did the primary task, desired impression, reference interpretation and stated boundaries change real design choices? Were those choices carried into content, hierarchy, density, behavior and responsive layout? Did later feedback change the intended part while preserving the rest?

Also inspect interaction quality. A beautiful output can contradict the person's priority; an obedient output can have an unusable correction flow. Naming the skill, asking a question, or producing a long rationale does not establish a good result.

## Original check examples

| Design promise | Exercise | Evidence and limitation |
| --- | --- | --- |
| Fast booking lookup | Find an existing booking by the supported identifier, then clear an unmatched query. | Actual results, filter preservation and recovery; visual inspection alone is insufficient. |
| Safe correction | Trigger a supported error, correct one field, return to review. | Entered information survives; the completion state matches the correction. |
| Dense overview | Compare several rows and perform a supported batch action; repeat on a narrow screen or zoomed view. | Necessary context remains accessible; a screenshot crop does not prove all content is reachable. |
| Calm, relevant character | Inspect real long content, an empty state and an error state, not only a hero. | Human assessment against the brief; no universal aesthetic score is asserted. |
| Usable controls | Operate the changed path by keyboard; inspect names, focus and status announcements where relevant. | Check the behavior; native semantics and custom widgets need different implementation work. |
| Browsing and collecting | Collect across filters, review picks, remove one and the final item, clear, return, and reload where persistence is promised. Repeat removal by keyboard. | Check selection/order and browsing context separately; focus must land on a usable control when the focused item disappears. Do not infer persistent selection from a temporary view filter. |
| Honest async outcome | Exercise loading, failure and retry/reconciliation paths the product supports. | No misleading success, lost input, or unsafe duplicate operation. |

For rendered implementations, check page identity, meaningful content, relevant console errors, the changed action and its resulting state. Inspect at least the relevant desktop/narrow layouts when the requested interface spans them. Capture screenshots where useful for visual comparison; distinguish them from interaction evidence. Report unavailable browser/assistive-technology checks without claiming full acceptance.

For a concept, check the described paths, content and constraints. Label unbuilt behavior and illustrative data. Do not claim a deployed result or measured usability.

## Evaluate this skill itself

Use realistic tasks and compare against the same inputs without the target skill. Include a vague brief, a sufficiently detailed brief, explicit creative delegation, and a narrow task that should preserve existing design. Use held-out examples when revising instructions.

When a task is a skill/library trial, assess the parent outcome separately from the example: did the findings improve the requested guidance, and did the example stay within its agreed scope? A successful product build does not establish that the master skill was improved. When the trial reaches its stopping point, return the supported lesson to the skill rather than extending product maintenance by default.

Inspect whether a question changes a consequential decision, respects known answers, permits an unexpected direction, and avoids unnecessary interruption. Inspect the completed artifact and its states after scripted answers. Keep outcome quality, answer fidelity, creative relevance, scope, and cost visible separately. Preserve ties and uncertainty; a small trial is not universal effectiveness evidence.
