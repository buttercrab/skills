# Taster: taxonomy, brand axes and diagnosis-to-rebuild workflow

## When to use

Select this when a brief calls for diagnosing generic interface patterns, composing a coherent system from brand/references, or rebuilding an existing page while retaining its content. Its taxonomy is particularly useful as a model of matching a screen part to the job it serves.

## What to inspect

Read the source/new/rebuild routes, taxonomy/pattern data contract and detector-level distinctions. Inspect the relevant brand, system and component-choice references before adopting one route. The same historical commit was inspected locally and fetched from the public repository; public pin is the portable reading path.

## What to borrow and adapt

Borrow explicit classification, a reason for each pattern, role-based tokens and consistency checks. Separate the owner’s brand from the design procedure’s defaults. For a mixed marketing-and-working interface, identify each surface’s use before composing it from a single family of components. Preserve source content and distinguish unsourced claims from real evidence.

## Mismatches and limits

Its fixed per-screen/component approvals, prescribed aesthetic bans, and automatic replacement of common fonts are contextual policies. They can conflict with explicit delegation or a supplied brand and are not imported by selection. A clean detector only means listed tells were absent; the source itself acknowledges that this does not prove good design. No detector, registry component, MCP tool or rebuild ran here.
