# Superpowers brainstorming: requirements before a design document

## When to use

Select this as a planning-method reference when the user requests requirements exploration or a design document. It helps an agent examine an unfamiliar project and expose decisions that would otherwise be silently filled with defaults.

## What to inspect

Read the question cadence, approach discussion, opt-out behavior and design-document gate together. Inspect the visual companion reference only when such a tool is relevant and authorized. The source’s workflow is more than a list of questions: it specifies what happens after answers and which activity it treats as approval-dependent.

## What to borrow and adapt

Borrow attention to the human’s actual description, explicit assumptions and competing approaches. Use project evidence to avoid asking settled questions. A short change can need a concise statement of direction rather than a full project dossier; communicate the consequential calls so the person can correct them.

## Mismatches and limits

The design-document approval gate and next-skill sequence are this workflow’s operational policy. They must not be imported automatically into a task where the user already authorized implementation or delegated choices. Menus can steer answers, but open questions can also demand too much abstraction; adapt to the person. No interview, companion server or downstream plan was executed in this inspection.
