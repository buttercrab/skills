# Repository-quality skill and library: implementation scope

Authorized by the user's “go” after the repository-library proposal, 2026-11-07.

Deliver a portable `repository-quality` skill with an annotated, searchable reference library. The skill should help an agent understand project context, ask consequential human-owned questions, trace real maintenance paths, select relevant examples and propose or implement only the requested improvements. Repository shape, CI configuration, executed checks and shipped artifacts remain different evidence.

## Research lanes

- Small/library/CLI contrasts across JavaScript/TypeScript, Python, Rust and Go; follow exact pinned source/manifests/tests/CI/distribution.
- Large/native/multi-package/community contrasts; inspect ownership, generated authority, test scope and publication units.
- Documentation/contribution and original research, with methods and context limits rather than universal metrics.
- Validation/packaging/releases and standards, including conditional cost and applicability.

Primary public sources only for technical claims. Existing deep-research dossiers provide leads and explicitly attributed historical evidence; new cards need substantive original annotations and actual inspection receipts. Root listings or repository popularity are not quality evidence. No upstream repository is modified, installed, built or tested by research lanes.

## Package and workflow

Use canonical Markdown cards with JSON metadata, generated human/agent indexes, and stdlib-only local search/validation. Discovery should permit direct browsing and contextual queries; no embedding service, database or global installation. The helper is package-local and independently validated; the existing design library remains unchanged.

Keep the core workflow compact and route detailed material through references. Cover stakeholder questions, actual change-path assessment, context-specific source selection, incremental proposals and promised verification. Distinguish repository maintainability from prescribing an entire system architecture, security audit or release operation.

## Evaluation and delivery

An independent author creates five small fictional repository fixtures before the workflow author reads them. Freeze the first package before fresh assessment runners receive the skill, raw repository fixtures and prompts. Assess output against actual provided facts, appropriate questions, source-to-decision transfer and bounded scope; preserve defects/ties/limits. No real product edits or external writes during evaluations. This is a first-edition developmental assessment, not a causal benchmark or exhaustive internet recall test.

Validate the helper, metadata, resource links, generated views, installer discovery and package portability. Save research coverage, revisions, access gaps, evaluation artifacts and limitations. Update the repository's inventory/tests for the new skill. Do not globally install skills, commit, push, publish, schedule work or resume Taster work.
