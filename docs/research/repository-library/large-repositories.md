# Large and multi-package repository cases

Research date: 2026-11-07. Ten purposively selected primary-source cases; 44 selected source/diff receipts in the cards, not 44 independent studies. Exact repository snapshots were resolved through the connected GitHub read API before file inspection. No upstream checkout, installer, executable, generator, build, test, browser session, CI trigger, package publication or remote write was performed.

The sampling contrasts native/runtime/compiler work, generated authority, multi-renderer contracts, module distribution, tooling workspaces and test registration. Popularity was not measured and is not a quality score. Existing deep-research work supplied possible case names, but the substantive receipts below were freshly read; the same Django revision remains current in the fetched branch result and its diff/helper were read again.

## Transfer and counterexamples

A source repository is not always the publication unit: Kubernetes stages several libraries, while SQLite distributes a generated amalgamation from a richer source tree. A default test command need not run the project's tests: VS Code deliberately redirects contributors to owning scripts. A file can be generated and still need review in a change: Go rewrites and LLVM expectations retain meaningful authoring inputs and semantic checks. A successful test can still omit an optional renderer: Django's helper makes that condition visible. A discovered C++ file need not register itself merely by existing: Godot force-links test units through generated code. These are inspected mechanisms; they do not establish that adopting them improves another repository.

The common recommendation is to trace a maintenance change from its authoritative input through actual validation/distribution boundaries and adapt the minimum useful mechanism. None of these cases establishes a universal directory layout, fixed CI matrix, governance policy or test-count target. Large-project examples are deliberately qualified for small teams.
