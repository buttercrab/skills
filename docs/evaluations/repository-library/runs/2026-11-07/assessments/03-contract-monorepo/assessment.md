Keep the present directories and independent SDK/gateway releases. First repair the committed SDK/schema mismatch and make every contract change reach generation, gateway and console checks. Version compatibility must be stated per release unit, not inferred from sharing a repository.

## Findings by practical consequence

1. **Observed generated contract drift.** `event.py` omits `source`, contradicting `event.json` and the explicit generator specification. The inspected constructor has no `source` parameter. Passing a schema-valid gateway payload directly as constructor keywords would therefore be incompatible by source inspection; no decoder/public parsing entrypoint is supplied, so this is not a demonstrated failure of a released decoding API. Existing two-field construction must remain supported when this is corrected.
2. **Configured CI does not establish contract reliability.** `.github/workflows/check.yml:4-9` runs gateway `npm test` only when the PR has label `gateway`. A schema change without that label does not select it; adding a label later is also not among the explicitly listed default PR event activities. The gateway script is `node --test`, but no test files are supplied, so there is no demonstrated assertion coverage. The SDK job (`:10-14`) compiles syntax; stale but valid dataclasses pass that kind of check. No supplied workflow regenerates/compares committed output, validates schema examples, tests SDK behavior, checks the console or checks an installed SDK artifact. This is a gap in the supplied configuration, not proof that no external checks exist.
3. **The supplied draft conflicts with clarified extension intent.** `docs/contract-change.md:1` permits missing `source` for non-gateway producers and withholds approval to require it. The console's gateway-specific type does not authorize changing the shared schema. The draft leaves unknown-field policy undecided, but the human answer now requires preserving unknown fields for round trips and documenting known fields. The current `additionalProperties:false` conflicts with treating an event containing future fields as schema-valid. Reconcile the schema, SDK parsing/serialization and documentation deliberately. `source` is already a known schema field and must not be confused with a future unknown field.
4. **Independent release compatibility is undocumented in the supplied snapshot.** Shared schema edits can land before each consumer ships, and committed versions do not reveal currently deployed/published combinations. Nothing supplied defines the supported older SDK/new gateway overlap, rollback window or cross-version acceptance cases. This is an evidence gap requiring a small explicit policy, not evidence of a failed release.

## Focused plan

1. **Restore the authoring-to-output path and record clarified policy.** Extend `docs/contract-change.md` with the schema → real generator/version → committed output map and real reproduction command once the omitted generator is available. Reconcile the optional `source` output with the specification. Keep `id`/`occurred_at` required and `source` optional. If `None` represents absence inside Python, encode omission on the wire rather than serializing `source:null`. Document known fields while preserving future unknown fields in SDK parse → serialize round trips, using a separate extras map with known-field collision precedence and nested values retained. Propose changing the schema's additional-properties policy to permit extensions while continuing to validate known properties; otherwise explicitly declare SDK tolerance broader than current schema conformance instead of claiming the strict schema already permits extras. Extend the real generator/templates to retain extras rather than hand-editing generated output. Verify old two-argument construction, optional present string, missing source, schema-invalid null, unknown nested fields surviving round trip and collisions with known names. Gateway currently projects three keys; the clarified requirement is for SDK users, so do not promise gateway pass-through without a separate change. Cost: one focused generator/schema/output/doc change, with generator availability an explicit prerequisite.
2. **Select checks by affected paths and assertions.** Make contract/generator/shared test changes select SDK, gateway and console checks without a manually applied gateway label; service-only and SDK-only work can retain focused routes. Add a deterministic regeneration comparison that fails on drift, including relevant newly created outputs. Add shared positive/negative payload examples and owning behavior tests: gateway default for absence, supplied string retention, SDK missing/present source, required-field failures at the supported validation boundary, and console rendering of actual gateway output. Include a negative drift specimen and an unlabeled schema-only PR in later workflow verification. Keep compileall as syntax feedback, not the contract gate. Cost: a small shared fixture set and three focused consumer routes, rather than a new general test framework.
3. **Write a per-unit compatibility/release record.** For each contract change, record schema revision, affected SDK/gateway versions, supported version pairs, optional/required semantics, minimum consumer capability and user-facing upgrade notes. Do not invent a single repository version. Obtain the supported overlap policy before choosing the compatibility matrix size. Reuse the same payload cases against the claimed older/newer combinations, with the SDK checked as an installed built artifact outside the checkout when that artifact is the distribution promise. For a gateway release, validate its candidate output plus co-deployed console and the supported SDK combinations; for an SDK release, validate its artifact against the supported gateway outputs and non-gateway producer cases. Check independent rollback compatibility as part of those pairs. Cost: one release checklist/record and checks for the supported overlap, not all historical versions.
4. **Stage compatible releases independently.** For this optional-field repair, preserving old constructor usage and missing-source acceptance is the candidate compatibility goal, subject to actual tests. Do not claim existing SDK 2.3.0 compatibility with new fields without its real artifact/API evidence. If an existing consumer rejects a proposed payload, release a compatible consumer first or defer emitting that payload for that supported combination; use expansion/deprecation steps for genuinely breaking changes. Each unit gets its own reviewed impact decision and release note. Gateway is pre-1.0, so document its actual stability promise rather than deriving one from the numeral; no arbitrary version bump is assigned here. Observe publication/deployment separately after later authorized release work. Cost: explicit sequencing only when compatibility requires it, retaining independent schedules.

No directory move, forced common release, package registry migration, release orchestrator, broad coverage target or Kubernetes-scale governance is warranted by these obstacles. A short change-impact record is the smaller starting point; automate its preparation only if recurring release effort justifies it.

## Human intent carried into the plan

Root supplied the human answer: “Keep source optional; preserve unknown fields for round trips, but document known fields. Keep independent releases.” The plan therefore selects SDK preservation rather than rejection, retains source optionality and independent release schedules, and explicitly reconciles the strict current schema with the new extensibility promise. The specific supported overlap duration/version pairs remain to be documented before setting an exhaustive release matrix; that does not block the focused plan or justify inventing historical compatibility.
