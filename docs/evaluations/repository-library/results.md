# Repository-quality library: delivery and assessment results

Date: 2026-11-07. Delivered the [repository-quality skill](../../../skills/repository-quality/SKILL.md), [48-card reference library](../../../skills/repository-quality/library/index.md) and [reading paths](../../../skills/repository-quality/library/PATHS.md). The deliverable is reusable repository guidance; source repositories remain read-only examples.

## What the first edition contains

25 repository cases, 17 guides, three studies, two tool/comparison entries and one standard. The cards contain 182 selected source links / 179 distinct URLs and approximately 13,400 original body words. These counts are reference units/locations, not independent studies or exhaustive internet coverage. [Curation coverage and source reviews](../../research/repository-library/index.md) distinguish fresh/retained inspection, selected artifacts, corrections, access gaps and weakly covered ecosystems.

The workflow elicits consequential context, follows a concrete maintenance/consumer change path, selects relevant reference mechanisms with mismatches, and returns a bounded assessment or requested improvement. It does not prescribe a universal folder tree, document checklist, quality score or monorepo. Source configuration, successful execution, packaged content, enforced review and release observation are separate claims. Examples in skill-development tasks must return findings to the parent deliverable rather than become a product-maintenance campaign.

The package is portable: canonical Markdown/JSON cards, deterministic human/agent indexes and a Python-stdlib-only helper for list/find/facets/show/build/validate. No database, embedding service or global installation is required. Existing design-library instructions and Taster work were not changed in this task.

## Assessment method

Five fictional repository snapshots were independently authored without reading the new skill/cards or source curation. The workflow author wrote the core instructions before inspecting case contents and froze the 61-file package before reading them. Each fresh non-forked runner received the frozen guide, only its request/raw source fixture and common effect/scope restrictions. Same inherited model/effort, no overrides; normal mandatory host guidance remained available. Case05 explicitly requested two independent bounded read-only child checks, whose reports were synthesized.

No fixture or upstream program, generator, test, build, package install, network call, registry operation or real-project edit was requested. Ordinary file inspection and the bundled catalog's read/search functions were permitted. A shared clarification made the distinction between file-reading utilities and banned project-command execution explicit. Case03 asked about unknown-field policy and received the exact scripted answer preserving optional source, unknown-field round trips and independent releases. Other private optional facts were not volunteered.

An independent reviewer, who authored neither the skill, source cards, fixture cases nor assessment outputs, receives the raw inputs, actual relays, final outputs, receipts/logs and evaluator notes. Judgments concern concrete source-path coverage, contextual reference transfer, proportional actions, human intent, evidence discipline and scope. There is no baseline and no causal-effect or general reliability claim. Cases are now development material, not an untouched future benchmark. [Protocol](protocol.md), [fixtures](fixtures.md) and the [frozen archive](runs/2026-11-07/README.md) preserve the method and limits.

## Scope gate

Cases02 (Python artifact) and03 (contract monorepo) self-report initial broad filename discovery that exposed sibling/evaluation paths. They report no sibling file-content reads and no upstream execution, but the common restriction also bounded discovery to assigned material. Under the frozen protocol **both outputs are excluded from acceptance conclusions**. Their assessments, receipts, source-derived findings and scripted answer handling are preserved diagnostically; useful content does not erase the deviation. No replacement run was silently substituted.

The remaining three cases are eligible for bounded source/plan review, subject to the review's findings. Logs/receipts are runner reports and coordinator summaries, not complete native tool transcripts or independently enforced filesystem isolation. No claim certifies every tool action or hidden-state exposure.

No material false runtime, installed-artifact, publication or protected-branch claim was found in the five written outputs. That is a bounded record judgment, not proof of every tool action or implementation correctness. All five explain contextual reference fit and mismatches; three remain eligible for acceptance conclusions under this protocol. No overall score, superiority, reliable future behavior or universal effectiveness follows. Compression and clearer optional-work ordering remain practical improvement targets; adding more references is not automatically a better assessment.

## Limits and next evidence

The first edition is strongest on GitHub-hosted libraries, CLIs, frameworks, native/compiler work, docs and mainstream packaging. It does not establish the quality of those whole repositories, actual upstream tests/releases/protections, or applicability across every language/team. Two empirical studies received fresh methods inspection; one historical coverage study preserves explicitly attributed earlier methods evidence with unsuccessful fresh follow-up. Three studies cannot establish an optimal repository workflow.

A source-only assessment can identify an input/configuration contradiction and propose a relevant later check. It cannot prove an installed artifact's behavior or a real contributor's comprehension. Future evaluations should use scoped discovery tooling that prevents sibling listings, fresh contexts/tasks, and separately authorized runtime or human-task measures when those outcomes are the question. No corrective work on an example repository is implied.
