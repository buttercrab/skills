# Attachment authorization migration decision

Review the proposed in-place endpoint seam and the enforcement gates below. This is a source-only decision brief and rollout plan; no migration or release was performed. Select the existing app/database/private-storage stack with an internal gateway adapter, no new datastore or service. Keep GET `/attachments/{opaque_id}`, session cookies, opaque IDs and byte responses. Move authorization by stable account cohort, preserving an irreversible security floor once a cohort enforces. ## Request ownership and compatibility

The existing app owns session verification, URL-to-row/storage-key resolution, response mapping and enforcement of the selected mode. The relational database remains authority for attachment metadata/ownership; preserve historical records and lookup behavior (`current.py:1,12`). The gateway team owns authorization decisions and sharing-policy freshness; the location/implementation of its policy store and update pipeline are unknown. Cohort routing and decision telemetry proposed below are app responsibilities, not a new gateway deployment.

Proposed enforcing flow: verify cookie; resolve attachment metadata; absent row returns 404; consult cohort state; call `authorize(account.id, opaque_id)` for an enforcing cohort. Allow reads the existing private object through the app and returns 200 bytes. Deny returns the same public 404 as absence. Unavailable, timeout or malformed/unknown decision yields 503 with no storage read. Storage failure after allow remains 503. Preserve existing invalid-session behavior rather than inventing a new response contract: it is not shown in the snapshot. Do not redirect to storage, disclose storage keys, add a client header requirement, or overwrite URLs.

In enforcing mode, ownership must not be an independent allow shortcut. Do not retain a pre-gateway non-owner denial if new sharing is intended to grant access to non-owners; retain the row and owner metadata instead. In legacy/shadow mode, retain the old ownership check and responses exactly. A revoked owner may receive 404 despite previously working URL: URL identity/retention compatibility does not override the explicit revocation policy. Confirm newly shared access with gateway fixtures supplied by its owner before enabling the sharing feature.

Propose no application authorization cache and no server retries for the initial pilot; a bounded gateway timeout maps to 503. Set its value from measured end-to-end budget and the approved regression gate, not from the gateway p95 budget alone. Old clients already retry twice; measure attempts and user downloads separately. No-cache avoids an additional stale allow copy but does not prove the gateway's 60-second freshness. Preserve private/non-cacheable response behavior or establish it before cutover; the snapshot does not establish HTTP intermediary caching behavior.

### Pilot abort policy and measurement

Use the human-supplied thresholds: abort pilot when its five-minute 503 rate exceeds its matched baseline by more than 0.2 percentage points; abort when download p95 rises by more than 200 ms for two consecutive five-minute windows; abort immediately on a confirmed authorization leak. The owner may tighten thresholds. Define matched baseline before pilot (same cohort/client mix, comparable workload/time, unchanged storage behavior); record request denominators and windows. Tag gateway and storage 503 causes internally while preserving the public 503. Client retries count as requests in the request-rate view; additionally measure logical download completion where client evidence exists. No such measurements were obtained here. The 503 threshold is a rate difference in percentage points, not a relative 0.2% change.

These thresholds resolve the frozen snapshot's missing numeric abort policy. Required pilot duration, minimum sample coverage, low-traffic treatment, and approval of recovery/re-expansion still need owner recording; avoid manufacturing a sample-size or success window. Aggregate availability thresholds never permit an authorization leak. A gateway 99.9% target alone does not establish an acceptable dependency impact or satisfy the pilot gates.

## Rollback and durable-state floor

Before any cohort enforces, disabling shadow may restore legacy execution because the policy explicitly permits shadow-only comparison. Once a cohort enforces, never route it back to `current.py` ownership-only code. Persist `ever_enforced` independently of a reversible rollout percentage. Read mode/floor from consistent authoritative DB state; do not let stale local flag caches turn off enforcement. State read failure must fail closed (503), not select legacy. A host binary that does not understand the security floor must not serve enforcing cohorts; retain the compatible enforcement adapter in any rollback artifact or hold those requests at a fail-closed handler.

For gateway failure, abort expansion and enter a degraded enforcing mode: disable the new sharing feature for that cohort (if an additional owner-only restriction is needed, it is an AND with gateway allow), keep gateway authorization for all surviving reads, return 503 when it is unavailable. For a confirmed leak or uncertain gateway correctness, block reads for affected enforcing cohorts with 503 until a trustworthy evaluator is restored; an outage is safer than restoring revoked access. After recovery, re-evaluate against current policies before resuming, verify revocations remain denied and review re-expansion evidence.

Rollback affects controls and feature exposure, not attachment bytes, storage keys, policy/revocation history or cohort enforcement history. Preserve additive fields, owner records and existing URL mappings; do not replay old policy state or backfill old owner permissions. Previously downloaded bytes cannot be recalled. Old clients continue cookie/GET/byte-response behavior and their known bounded 503 retries; revoked requests get 404, dependency outage gets 503. They may lose availability during degraded rollback, as mandated, but cannot silently regain access. Control failure, stale mode and older-binary rollback are explicit acceptance scenarios.

## Alternatives and decision bounds

| Option | Fit and decisive tradeoff | Decision |
|---|---|---|
| In-place endpoint adapter + gradual sticky cohorts | Preserves client protocol and data authority, isolates gateway seam with low new operations burden; adds gateway latency/availability dependence and fleet-control correctness work. | Selected proposal under evidence gates. |
| One-shot switch of all accounts | Same simple components but maximizes impact before old-client/freshness behavior is evidenced; gives no staged comparison. | Defer unless gateway readiness and complete representative evidence justify scope. |
| New endpoint/proxy plus redirects or signed public object URLs | Can offload app bytes but old mobile clients cannot redirect/new-header; public URLs violate policy and complicate revocation. Another proxy adds operations without a required seam benefit. | Reject under supplied contract; no vendor selection needed. |
| Ownership fallback or cached allow on gateway failure | Improves apparent availability but may revive revoked access; TTL alone cannot repair unspecified gateway freshness. Shared cache exceeds budget; local copies add stale state. | Reject fallback; defer caching until a measured need and proven total freshness bound exist. |
| Remain owner-only/no cutover | Simplest operations and useful shadow baseline, but cannot fulfill mandatory gateway authorization/revocation target. | Safe temporary pre-enforcement state, not completion. |

Unknowns that block a credible readiness claim: gateway evaluated-version interface and update/freshness semantics; definition of revocation for in-flight reads; runtime policy storage and cross-fleet control consistency; actual workload/latency/availability; download/intermediary caching; retention length and invalid-session behavior. Security/gateway owners must define whether “within 60 seconds” governs read start, response-byte release or termination of existing transfers. Measure from authoritative policy commit through gateway observation, app decision and applicable byte boundary; no invented TTL or no-cache assertion proves this. Until clarified and evidenced, mark revocation acceptance unresolved.
