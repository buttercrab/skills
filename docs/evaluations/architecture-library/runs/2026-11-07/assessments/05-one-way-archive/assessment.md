# One-way archive transfer proposal

Status: source-only architecture proposal, not an implemented or measured system. Select application-owned transfer identities, durable per-domain ledgers, replay-safe A-local commits, and the already approved daily paper acknowledgment. No broker, product, new network return path, or shared writable store is needed. Editable lifecycle diagrams are in `diagrams.md`.

The proposal depends on that final unknown: receiving and quarantining bytes is feasible under the supplied contract, but admitting them as **approved records** is conditional on an established authenticity/approval-verification mechanism. Do not claim compliance by trusting a digest or the one-way direction. Proposed signed manifests need an approved trust root, enrollment/rotation/revocation and assurance that the signer binds the export approval decision to the intended payload. Evidence resolving this gap is an approved trust/enrollment contract and its verified implementation. No such capability is assumed or deployed here. ## Ownership and transfer contract (proposed)

S owns originals, approval selection, manifest identity, send-attempt history, acknowledgment entries and retention deadlines. A owns quarantine, validation, immutable archived versions, durable processing identities and committed receipts. The device owns transport only. The custodian conveys committed receipt information on paper and S's authenticated operator transcribes it; neither is a network response.

1. Persist immutable export objects and a manifest before marking a transfer ready. Use a stable, opaque transfer ID independent of filenames and wall clocks. Bind manifest schema version, record ID/version ID, approval decision ID, object length and cryptographic digest, ordered membership, total counts and bytes into a canonical manifest digest. Define encoding/canonicalization and hash algorithm in the proposed format; they are not supplied facts. Transfer ID and exact manifest digest identify the same intent across retransmissions. Changed membership or corrected record versions require a new manifest/transfer ID.
2. Package each ≤250 MB object separately with bounded framing overhead so each submitted file remains ≤300 MB. Split large manifests into independently identified parts with a root manifest listing all parts and digests; bound every file size before admission. Daily 12 GB is not a single file. Filenames are routing hints only. Capture landing files into unique local staging objects before processing so repeated filenames do not become processing identities. Device landing overwrite/atomic-file-completion semantics are unspecified: implementation must establish safe ingestion or tolerate a missing/corrupt object and request reviewed retransmission through the operator workflow. Do not assume every emitted file can be recovered from that directory.
3. Record submission attempts separately from immutable intent; device acceptance or a local write means `SubmittedAwaitingEvidence`, never `Archived`. A crash around submission leaves the send attempt uncertain. Resume local preparation safely, but an export retransmission goes through human review as required. No automated delivery retry policy silently bypasses that review.
4. A stages and verifies bounds, completeness, encoding, digests and authentic approval binding. Reordered root/parts/objects wait in `Incomplete`; corruption or identity/content conflict goes to quarantine. Independent clocks and filename timestamps decide neither identity nor version order. Multiple versions remain distinct immutable archive entries; a replay of an older version cannot overwrite a newer version.
5. Enforce A-local unique keys for record ID/version ID and transfer ID plus manifest binding. On the same key with identical immutable bytes/binding, return existing progress/receipt; on differing bytes, approval binding or manifest, quarantine the conflict. Serialize concurrent duplicates using local constraints/transactions, not a check-then-insert outside the commit. A validates and commits each archive record and matching receipt record together using the supplied transaction capability. If payload bytes live outside that DB, safe durable placement before reference commit and recovery/verification are additional unestablished capabilities; prefer keeping the archive effect in the stated transaction boundary for this proposal.
6. A may print a **complete transfer** receipt only once every manifest member has a committed verified archive/receipt record and the complete membership/count/digest has been checked. Propose a locally durable aggregate receipt/finalization step serialized against membership changes; keep immutable transfer membership and member receipts so crashes can resume finalization. Availability of an aggregate transaction/consistent query is an implementation obligation, not inferred from the specified per-record transaction. If only per-record transactions can be established, print member receipts, and S acknowledges the transfer only when it has matched all members. Partial completion must never produce a complete-transfer acknowledgment.

Deduplication is a scoped A-local archive effect guarantee, conditional on actual atomic constraints and durable storage. It is not end-to-end exactly-once delivery or an unconditional delivery guarantee. Keep compact transfer/version deduplication bindings as long as archived versions can be replayed; do not expire them merely because S's 45-day retention has elapsed. Capacity for these permanent compact identities has not been quantified.

## Paper acknowledgment and uncertainty (proposed)

A receipt prints only transfer ID, canonical manifest digest and member count, all permitted paper fields. Print it from committed verified receipt data, after finalization; if interrupted, reprint the same receipt. No record content or failure-detail payload crosses back. An incomplete/quarantined transfer produces no complete acknowledgment. A's local UI can show detailed quarantine causes to its local operator; S cannot remotely query that UI.

S entry is an authenticated local action with an audit trail. Exact-match the ID, full digest and expected count to one retained manifest, show the matched transfer summary, and require the operator to compare the paper before confirmation. Reject malformed/mismatched/unknown values and keep a rejected-entry audit trail without starting retention. Identical repeated entry is a no-op: preserve the first valid acknowledgment and deadline. A plausible typo selecting another valid entry is not prevented by local authentication or a checksum alone; compare all three fields to the actual paper, use a separate confirmation/review step for corrections, and never infer authenticity of paper from a digest. The approved human custody process is the acknowledgment trust boundary; stronger anti-forgery assurance is not established.

S records acknowledgment using its own local time and starts 45 full days of retention there, conservatively never earlier than confirmation. Archive-side time is not used to subtract retention because the clocks differ. A reported receipt can be delayed, misplaced, reprinted or entered twice; that changes S's knowledge, not A's committed archive state. While S has no valid acknowledgment, its state remains `SubmittedAwaitingEvidence` even if A has already archived everything. A timeout/age alert is never proof of loss or permission to delete. If a mistaken acknowledgment is discovered, flag and suspend deletion pending correction; audit invalidation and require fresh confirmation. Repeated valid entry must not silently reset the original deadline. Do not promise restoration after deletion.

## Operator recovery and capacity

S lists aging unacknowledged transfers with manifest IDs, outstanding acknowledgment status and local capacity; A lists incomplete/quarantined transfers and committed receipts. Custodian checks A locally on the approved daily round, carrying/reprinting eligible receipt lines only. If no valid receipt appears, S's authenticated operator reviews the retained manifest and send attempts, records the review and resubmits identical content under the same transfer ID. This is safe for an already committed A transfer under the proposed local idempotence contract. It does not require first proving non-delivery, which S cannot do. Missing parts may be retransmitted under the unchanged manifest; exact part-selection knowledge at S is limited because paper is restricted to IDs/digests/counts. Whole-transfer resend remains the simple recovery option. Corruption repeats or identity conflicts require local investigation; changing intent creates a new transfer.

A 36-hour transport delay plus a daily paper round can leave S unacknowledged after archival; a reviewed resend can overlap delayed originals. Do not classify an export as lost simply because it misses a paper round or the two-working-day objective. No transport receipt establishes completion. Loss can repeat indefinitely under the spec, so the 95% SLO cannot be proven from these semantics alone. Measure archival completion separately from S acknowledgment lag; any cross-clock age comparison needs the stated 20-minute uncertainty and a defined working-day calendar. Observations of actual transport loss/delay, archive processing and review/custodian timing would establish feasibility; none were measured.

The existing 90-day capacity is a buffer, not authority to delete pending transfers or a capacity guarantee for originals plus staging, quarantines and retransmissions. At a configured safe admission threshold, stop preparing new exports and surface a local capacity escalation; retain originals/manifests and existing pending work. Exact storage headroom/admission thresholds need actual footprint evidence. A permanent outage cannot satisfy both unlimited continued exports and finite retention storage. No invented emergency purge policy is proposed.

## Alternatives, transition and follow-up evidence

Keep one application and existing durable store per domain with local responsibilities, rather than adding services for two maintainers. Keeping the prototype is rejected because deletion is independent of explicit acknowledgment, duplicates repeat imports, and counts do not verify content (`snapshot/current-state.md:2`; `snapshot/approved-constraints.md:4-6`). A synchronous acknowledgment, return broker, shared status DB or automated A→S polling contradicts the approved boundary. Automatic blind retries are rejected by the human-review rule; reviewed replay using stable identity is selected. Cryptographic signing is conditional rather than treated as a completed authenticity solution.

Proposed transition: suspend prototype's seven-day purge before migration; inventory retained originals/manifests and uncertain legacy imports locally; establish manifest/receipt format and trust mechanism; add A deduplication and receipt commit behavior; add S paper entry/retention UI; reconcile legacy imports before issuing any new verified receipt. Past deletion is not recoverable from this snapshot, and “Imported” counts cannot retroactively establish verified approval. Avoid mixed legacy/new imports bypassing identity checks. Rollback must preserve manifests, ledger bindings, receipt records and retention holds; reverting code cannot undo a committed archive or valid paper acknowledgment. These are proposed steps, not actions performed.

Required future checks, not executed: delayed duplicate and out-of-order members; filename collision and partial landing files; corrupt bytes and forged manifests; same identity/different bytes; crash before/after member and aggregate receipt commits; print interruption; concurrent replay; wrong and duplicate manual entry; working-day/time skew; long outage/storage pressure; preservation of versions and legacy reconciliation. Confirm local durability semantics, transaction granularity and data-placement behavior before claiming those guarantees.
