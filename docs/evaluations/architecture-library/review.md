## Per-case original judgments

### A01 — desk ledger

**Judgment: substantive proposal supported; original diagram delivery incomplete.** Scope gate: eligible on reported evidence.

The proposal uses the actual envelope—one shared desktop without concurrent edits, small weekday imports, offline use, simple queries and two engineer-hours/month—to retain one local application and authoritative SQLite store. It compares independent services on coordination and operational cost rather than choosing by a service-count rule. Reopening conditions are concrete: concurrent/remote edits, independent delivery, measured bottlenecks or changed recovery needs. The preview/approval gap is correctly inspected, and exact-preview approval plus committed import identity are explicitly proposals, not current behavior.

The response correctly separates transaction interruption from hardware loss, a missing success display from a failed commit, and local availability from off-device backup freshness. It treats the recorded 14-minute drill as historical evidence and warns that an offline share can threaten the prior-business-day recovery objective. It does not infer durability from `with db` alone. Source basis: `cases/01-desk-ledger/snapshot/requirements.md:2-11`, `operations.toml:1-15`, `ledger.py:5-19`; delivered assessment sections “Selected boundaries and guarantees,” “Backup,” and “Alternatives and reopening conditions.”

Diagram meanings agree with the proposal: approval, invalid input, commit-observation uncertainty, offline backup and separate storage-loss recovery are all covered. However, original diagrams 2 and 3 fail parsing; only the context flowchart parses. Thus the requested validation/crash runtime diagrams are not usable Mermaid as delivered. This is the material miss. The proposal is also longer than the requested short decision brief; condensing the main operator/maintainer decision would improve proportionality, but no extra architectural machinery is required. Complete validation, schema/settings, storage assumptions, performance and restore behavior remain unverified, appropriately labeled.

Source basis: `cases/02-refund-queue/snapshot/worker.py:3-16`, `contracts.md:2-6`, `policy.md:2-8`; delivered “Proposed authority and commit boundaries,” “Proposed execution and recovery rules,” and “Safe transition.”

### A04 — compatible rollout

**Judgment: substantive migration proposal supported; original diagram delivery incomplete.** Scope gate: eligible on reported evidence.

The selected existing-endpoint adapter preserves GET/cookie/bytes and historical metadata/URLs, avoiding redirects, new headers and public object URLs. Stable cohorts and proposed durable `ever_enforced` state give rollback a security floor. Older binaries, stale flags and unavailable control reads cannot silently restore ownership-only access. Additive observability, shadow comparisons and acceptance gates fit the existing fleet/DB and staffing envelope; proposed six-week work is not claimed execution. Source basis: `cases/04-compatible-rollout/snapshot/contracts.md:2-6`, `current.py:2-12`, `migration-policy.md:2-10`; delivered request ownership, rollout, abort and rollback sections.

The latter preserves the security floor, but does not replace the broken requested request/authorization view. Broad enforcement readiness is correctly withheld pending evidence.
