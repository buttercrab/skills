## Requested deliverable

The user asked to improve the master `design-with-intent` skill using the trial's lessons and explicitly stop work on Taster. ## Supported lessons and changes

| Observed issue or decision | Instruction change | Limit |
| --- | --- | --- |
| The library trial grew into product implementation and dependency/QA work; the user became unsure which skill was being improved. | Keep the parent deliverable distinct from an example; bound a trial's purpose/stopping point, return its findings to the parent, and name the actual artifact in updates/results. | An explicitly authorized product task remains valid; this does not introduce mandatory approvals or ban real-project trials. |
| A delayed answer selected pattern browsing after a provisional diagnosis proposal; a further answer selected visual browsing after a purpose-first sketch. | Attach async replies to the decisions they answer, retire superseded dependent questions/proposals and avoid duplicating pending questions across channels. | Minor reversible assumptions and explicit creative delegation remain supported. Time passing still does not answer a required question. |
| A variant-navigation event showed the purpose-first sketch while the user explicitly chose visual browsing/collecting. | Distinguish inspection/navigation from preference endorsement; explicit human direction controls the revision. | Explicit selection actions can communicate a real choice; merely displaying an option does not. |
| Explanatory task-first proposals did not express the user's desired visual exploration. | Separate task matching, visual affinity/collection and shortlist comparison; use actual inspected samples for visual choice, with suitability available in detail when appropriate. | Visual-first browsing is a response to this goal, not a default for every catalog. |
| The project already had usable preview, collection, comparison and handoff mechanisms. | Inspect existing assets/flows before replacing them with a famous product's framing; require references to support a particular decision. | Existing behavior can still need replacement when evidence warrants it. |
| Runtime checking found focus dropped to BODY when a removed item unmounted. | Add conditional collection checks for keyboard removal, last-item/empty recovery, selection/order, browsing context and promised persistence. | Product QA does not establish the master skill's general effectiveness or accessibility conformance. |

The existing real-project record retains the original proposal, human steering, implementation and bounded QA evidence. No empirical improvement percentage, universal aesthetic rule or new curated resource is inferred from this one development case.
